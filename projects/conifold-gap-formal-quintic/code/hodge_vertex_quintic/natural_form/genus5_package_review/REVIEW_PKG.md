# Review of cluster_genus5_quintic as a cluster deployment (2026-11-11)

Scope: the shell scripts (env.sh, V_validate.sh, S_array.sh, C_collect.sh, submit_genus5.sh), the new Python files (genus5_run.py,
g5_engine.py, g5_checks.py, g5_validate.py, g5_graphs.py, make_refdata.py) and the Python-version behaviour of the whole package.
Nothing in cluster_genus5_quintic/ or in the project folders was modified. All tests ran in the copy `genus5_package_review/pkg/`
(byte-identical *.py and *.sh, md5 checked), with review helpers in `genus5_package_review/pkg_tools/` (python3 shim, fake Lmod `module`,
fake `sbatch`, memory probe, logs of the end-to-end test in `pkg_tools/e2e/`).

**Verdict: no BUG found. The package is ready to deploy.** There are two RISK items, both about the cluster environment and both
caught early by V_validate.sh or a quick `ls`. The MINOR items are documentation or cosmetic. The genus-4 end-to-end test
reproduces the table of record exactly. It covered 5 array tasks through S_array.sh, one task killed midway and resumed, and
collect with the additivity check.

## 1. Bash / SLURM

| # | Item | Verdict | Evidence |
|---|------|---------|----------|
| 1.1 | Line endings of the *.sh files | OK | No CR byte in any *.sh, README.txt or data/*.json (checked byte-wise with `cat -A` and a Python byte scan). Some project modules (fq3_m.py, fq4_split.py, fq_fp.py, ...) have CRLF line endings. Python reads them with universal newlines, so this does no harm. All files are pure ASCII. |
| 1.2 | env.sh sourced without `set -e` | OK | None of the job scripts sets `-e`, so a failing `module load` or `module unload` inside the loop cannot abort the job. env.sh ends with `echo`, so `source ./env.sh \|\| exit 1` sees status 0 on success. |
| 1.3 | `return 1 2>/dev/null \|\| exit 1` | OK | Tested both ways. When sourced, env.sh returns 1, the caller's `\|\| exit 1` fires and the job ends with "no Python >= 3.8 found ...". When run with `bash env.sh`, it exits with 1. |
| 1.4 | Lmod `module -t avail Python` (stderr, markers) | OK | `2>&1` catches Lmod's stderr output. A fake `module` function printed a module-path header, `Python/2.7.18-...`, `Python/3.10.8-GCCcore-12.2.0`, `...-bare`, `Python/3.11.3-GCCcore-12.3.0 (D)` and `Python/3.12.3-GCCcore-13.3.0(default)`. The grep then sort -V -r loop worked through the candidates. `...(default)` failed to load and was unloaded. `(D)` became its own word, failed harmlessly and was skipped. The script then loaded Python/3.11.3 and set PY=python3. Test output is in the transcript; the fake is `pkg_tools/fake_module.sh`. |
| 1.5 | No module matches / no `module` command | OK | The clear error message goes to stderr and every job exits within seconds. With an old system python3 (exit 1) and no module, the message appears and the exit code is 1. |
| 1.6 | Module-system init fallback | RISK (low) | If the batch shell lacks the `module` function, env.sh tries /etc/profile.d/modules.sh, /usr/share/lmod/lmod/init/bash and /usr/share/Modules/init/bash. EPEL Lmod installs `/etc/profile.d/z00_lmod.sh`, and EasyBuild-installed Lmod uses `$LMOD_PKG/init/bash`; neither is in the list. In practice SLURM's default `--export=ALL` passes the `module` function from the login shell, so the fallback is rarely needed. If it is needed and fails, every task ends at once with the message from 1.5. That is a lost queue slot, not a wrong result, and V_validate.sh (same env.sh) shows it first. Possible hardening: add `"$LMOD_PKG/init/bash" /etc/profile.d/z00_lmod.sh` to the list, or strip markers with `sed 's/[ (].*//'`. Not required. |
| 1.7 | Stanage system python3 | OK | On Rocky 8, /usr/bin/python3 is 3.6. `g5_pyok` rejects it and the module loop runs. If a 3.6 interpreter were still used, all modules parse with the 3.6 grammar (checked with `ast.parse(..., feature_version=(3, 6))`), so genus5_run.py reaches its own clean "needs Python >= 3.8" exit. |
| 1.8 | S_array.sh argument passing | OK | `NT="$1"; shift`, then `--genus 5 "$@" --task $SLURM_ARRAY_TASK_ID --ntasks $NT`. Tested: `S_array.sh 50 --genus 4 --prime 89 --variant nat --ab 1/3,-2/7` produced tag `g4_89_nat_ab1o3_m2o7`, so a later `--genus` overrides the default and the comma value arrives as one word. sbatch stops parsing options at the script name, so `--prime` and the other flags after it reach the script. The fake-sbatch dry run of `submit_genus5.sh all 100` shows the exact argv: `[S_array.sh] [100] [--prime] [89] [--variant] [nat] [--ab] [1/3,-2/7]`. |
| 1.9 | `--ab` value starting with a minus sign | MINOR | In Python 3.8 to 3.12, argparse treats `-1/3,2/7` as an option string ("expected one argument"). Its negative-number regex only accepts `-\d+` and `-\d*\.\d+`. Python 3.14 on the workstation accepts it, which is why the test passed here. The shipped frame `1/3,-2/7` is not affected. For a frame with negative alpha, write `--ab=-1/3,2/7` (also tested). Worth one line in the README. |
| 1.10 | 0-based arrays | OK | submit uses `--array=0-$((nt-1))`. The README resubmission example uses explicit indices. `${SLURM_ARRAY_TASK_ID:?...}` aborts outside an array. An index >= N raises IndexError at once and writes nothing. |
| 1.11 | `--output=logs/slurm/...` must exist at submission | RISK (low) | SLURM does not create the directory. If it is missing, the job cannot open its output file and fails with no log. submit_genus5.sh runs `mkdir -p logs/slurm`, but README step 1 submits V_validate.sh directly before that. The shipped folder does contain logs/slurm/ (holding only desktop.ini), and tar keeps empty directories, so a tarball of the folder is fine. The risk is a re-packed tarball or a fresh `git`/rsync copy without it. Fix: add `mkdir -p logs/slurm` to README step 1, or ship a `logs/slurm/.keep`. |
| 1.12 | Submission directory | MINOR | All scripts `cd "$SLURM_SUBMIT_DIR"`, and the relative `--output` path also depends on it. A manual `sbatch` (V_validate, a resubmission, collect) must be run from the package directory. The README implies this but does not say it. (The `$(dirname "$0")` fallback would point to slurmd's spool copy, but SLURM_SUBMIT_DIR is always set in a job, so the fallback is never used.) |
| 1.13 | `--parsable`, afterany on an array job | OK | `${jid%%;*}` strips the `;cluster` suffix. Dry run with a fake sbatch printing `1001;stanage` gave `--dependency=afterany:1001`. On an array job ID, afterany waits for every element. set -e stops submit_genus5.sh if an sbatch call fails, although runs already submitted stay in the queue (MINOR, obvious from the echo lines). A wrong mode prints usage, exits 1 and submits nothing. |
| 1.14 | Executable bits | OK | Not needed: everything is started with `bash` or `sbatch`, and all scripts begin with `#!/bin/bash`. |
| 1.15 | Log host name | MINOR | The logs print `os.environ["HOSTNAME"]`. Under `--export=ALL`, SLURM jobs usually inherit the login node's HOSTNAME, so task and validation logs may name the login node. `socket.gethostname()` or `SLURMD_NODENAME` would be correct. Cosmetic only. |
| 1.16 | Time and memory limits | OK | Memory was measured on the heaviest genus-5 inner graph, 3897 (E=10, V=6, 21 decoration combos, 2536 s estimated). Peak working set was 85 MB including set-up, with at most 3125 frontier keys x 32 subsets = 100000 live series. Graph 2134 peaked at 56 MB. `--mem=2G` per task leaves more than 20x headroom. The heaviest task is 0.70 h x f, against a 48 h limit. Optional: a shorter `--time` (for example 8:00:00 for arrays, 1:00:00 for validate and collect) would help backfill scheduling. Collect at 8G is ample (the parts are tens of MB of JSON). |

## 2. Python 3.8 compatibility and platform independence

| # | Item | Verdict | Evidence |
|---|------|---------|----------|
| 2.1 | Grammar | OK | `ast.parse(src, feature_version=(3, 8))` succeeds on all 32 *.py files, and so do (3, 7) and (3, 6). There are no f-string format specs, no walrus, no `match`, no dict-union `\|` and no runtime generics `list[int]`. |
| 2.2 | Library features | OK | An AST scan of every module attribute and import found only: `math.comb/isqrt/prod/factorial` (3.8), `functools.lru_cache(maxsize=None)`, `itertools.{product,permutations,combinations,combinations_with_replacement}`, `os.replace/makedirs(exist_ok)`, `multiprocessing.Pool` (as a context manager), `random.Random(int)`, `json`, `re.match`, `argparse`. Not used: removeprefix, math.lcm, zip(strict), functools.cache, int.bit_count (POPC table and `bin().count` are used instead), Fraction format specs. `pow(x, -1, p)` (3.8) appears only in make_refdata.py, which is off the run path, and it is valid in 3.8 anyway. |
| 2.3 | multiprocessing start methods | OK | Pools are used only by `--validate` and `--run`. Workers need `genus5_run.job` and `_CACHE`. With fork (Linux, Python <= 3.13) the cache is inherited. With spawn (Windows, already validated) and forkserver (Linux default from 3.14), each worker rebuilds the Split on first use, and the monkeypatch in make_split is reapplied there. `-I -B` reaches the workers, and sys.path goes with spawn's preparation data. |
| 2.4 | Hash randomisation | OK | No set or dict of strings controls any ordering that matters. Sets are of ints or int tuples, whose hashes are not randomised; `decorations` sorts its permutations; `Split.graph` iterates a set of int tuples, which only changes the order of an exact integer sum. |
| 2.5 | Locale / encoding | OK | All files are ASCII and json.dump writes ASCII, so `open()` without `encoding=` is safe under LANG=C. The logs are opened with utf-8. |
| 2.6 | Windows dependencies on the run path | OK | Paths are built with `os.path.join` from `__file__`. There is no ctypes, os.startfile, msvcrt, winreg or backslash literal. The tmp-file-then-`os.replace` pattern relies on CPython closing the unreferenced file object when `json.dump` returns. That works on Windows, where replacing an open file would fail, so it works on Linux too. |
| 2.7 | Cross-version determinism of the arithmetic | OK | Everything is exact integer arithmetic mod p. `random.Random(1)` root splitting in fq_scalar_lib uses an int seed, which gives the same stream on 3.8 and 3.14. V_validate.sh compares genus 2 to 4 tables against the stored results with the cluster's own interpreter, and that is the guard. The shipped id parts (Python 3.14, Windows) are therefore valid references for the additivity check. |

## 3. Logic

| # | Item | Verdict | Evidence |
|---|------|---------|----------|
| 3.1 | Task assignment determinism | OK | `lpt_assign` sorts by `(-cost, t)` and picks `min` by `(load, j)`, so float ties fall to the index. Float accumulation follows a fixed order and is deterministic under IEEE. Feeding the cost dict in reversed insertion order gives the same 100 slices. The slices partition range(4555). Heaviest task 0.704 h, mean 0.462 h (reference machine). Genus <= 4 uses uniform costs. |
| 3.2 | Resumability and atomic writes | OK | After each inner graph the whole part file is rewritten to `<path>.tmp<pid>` and then moved with `os.replace`. A kill during the write leaves a tmp file, which read_parts ignores (regex `^(task\d+of\d+\|local)\.json$`; tested with a truncated `task1of5.json.tmp999`). A resubmitted task skips the graphs already stored. There is no fsync, so after a node crash (not a SLURM kill) a zero-length file is conceivable on a network filesystem. json.load would then raise loudly. Remedy: delete that file and resubmit. Not worth hardening. |
| 3.3 | Concurrent writers | OK | Each task writes only `parts/<tag>/task<I>of<N>.json`, its tmp file and `logs/<tag>/task<I>.log`. `os.makedirs(..., exist_ok=True)` tolerates the race between tasks. Accidental double submission of the same (tag, N, I) yields identical content, and the tmp names differ by pid. MINOR: two runs of one tag with different N append to the same `logs/<tag>/task<I>.log`, because the log name has no N. |
| 3.4 | Collect: partial coverage, duplicates | OK | Tested. With task 2 cut at 32 of 76 graphs, collect printed `FAIL all 379 inner graphs are covered: 44 missing, e.g. [162, 167, ...]`, and the vertex, regularity, GAP and ADDITIVITY checks failed with the same graphs named. The run then ended with `FAILURES`. An identical duplicate under another N (`task0of1.json`) was merged and counted once. A duplicate with one altered residue raised `AssertionError: inner graph 0 occurs in two part files with different content`. |
| 3.5 | Additivity against the shipped id parts | OK | `parts/g5_89_id/local.json` and `parts/g5_61_id/local.json` each hold 4555 inner graphs with the right tag, every piece in the form `{t: {t: [8 residues]}}`. The check runs only when the variant is not id, maxout is None and the id run of the same tag is complete. Otherwise it logs "skipped": for the second frame, whose id tag `g5_89_id_ab1o3_m2o7` does not exist, as the README says, and for the maxout controls. Tested at genus 4 after a local `--run` of `g4_89_id`: PASS. |
| 3.6 | id variant in `--task` mode | OK | `compute` returns `{str(t): graph_id(sp, t)}`. A genus-4 `--variant id --task 0 --ntasks 50` part merged with an existing `local.json` (379 graphs, duplicates identical). `--maxout` with id is refused. |
| 3.7 | maxout semantics | OK | `cap = min(K-1, maxout)`. A series branches to outer only while `POPC[S] < cap`, so |S| <= cap. An outer graph with E <= m gets contributions only from subsets of size E, so it is exact. The vertex graph (S empty) is exact. Regularity is tested on `i >= 1` with `E_i <= maxout`; index 0 is the unique E=0 graph because the lists are sorted by (E, key). With maxout=None, the cap K-1 = 7 drops subsets with >= 8 outer edges. That is exact because E_out = O(u), which is checked and also asserted in Split. GAP and total are skipped for maxout runs. |
| 3.8 | Regularity, gap, vertex checks | OK | Regularity requires `[u^0..u^(2g-3)]` = 0 for every tested outer graph, with all K = 8 coefficients compared. Gap requires `t_c^-7..t_c^-1` = 0 in the total. The vertex graph must be `c t_c^-8 + 0 + ...`. A mismatch of c with the Bernoulli pattern is reported as EQUAL/DIFFERENT and is not a failure (by design). Non-regular graphs are printed with their coefficients (first 40). |
| 3.9 | Tag naming | OK | Tags: `g5_89_nat`, `g5_61_nat`, `g5_89_M0_out2`, `g5_89_nat_t7_out2`, `g5_89_nat_ab1o3_m2o7`, `g5_89_id`. They are distinct, and the genus, prime, variant, frame and maxout that determine the computation all appear in the tag. Different spellings of the same frame (for example `0/1,0`) would give different tags but never a collision. |
| 3.10 | Cost table for controls | OK | M0 and nat_t7 with maxout 2 reuse `est_dp`, the full cost. With 20 tasks the heaviest estimate is 2.3 h x f, which is an upper bound since maxout only cuts work. The 48 h limit is far away. |
| 3.11 | Validation coverage | OK | V_validate.sh checks the cluster interpreter on genus 2 to 4 against the stored tables (8 genus-4 runs, all 379 outer graphs through u^5), the genus-5 set-up at both primes, and the calibration. It uses the same env.sh, so environment problems surface there first. |

## 4. End-to-end reproduction at genus 4 (in the copy)

Setup: a python3 shim on PATH (`exec py "$@"`), `SLURM_SUBMIT_DIR=<copy>`, no `module` command. env.sh found the shim: "env.sh: using ...Python314 3.14.6".

1. Reference for additivity: `genus5_run.py --genus 4 --prime 89 --variant id --run --nproc 1` (40 s). Its collect passed, with a gap of 1/180000 t_c^-6.
2. `SLURM_ARRAY_TASK_ID=i bash S_array.sh 5 --genus 4 --prime 89 --variant nat` for i = 0, 1, 3, 4, run in parallel: 76/76/76/75 inner graphs, 94 to 117 s each, all "COMPLETE".
3. Task 2 was started, its python process was force-killed after 33 graphs (no tmp file left behind), and the last stored entry (graph 162) was deleted by hand to simulate a lost write: 32 of 76 remained.
4. Collect on this partial state reported 44 missing graphs, and all dependent checks failed with the missing graphs named (see 3.4).
5. Task 2 resubmitted: "resuming: 32 done", 44 graphs computed, "TASK 2 OF 5 (g4_89_nat) COMPLETE: 76 inner graphs".
6. `bash C_collect.sh --genus 4 --prime 89 --variant nat`: coverage 379/379, E_out = O(u), frozen symbol, VERTEX (1/180000) t_c^-6 + 0 + ... + 0, REGULARITY (378 outer graphs), GAP, ADDITIVITY against g4_89_id: **ALL CHECKS PASSED**.
7. Comparison of `results/g4_89_nat.json` with `data/ref_g4.json["g4_89_nat"]`, keyed by `json.dumps([gv, ed])`: 379 outer graphs, **0 mismatches**, no extra keys, and the total identical to the stored total.
8. `submit_genus5.sh all 100` with a fake sbatch printing `<id>;stanage`: the 5 arrays and 5 collect jobs had the right argv and afterany dependencies (see 1.13). An unknown mode printed usage, exited 1 and submitted nothing.

Logs: `pkg_tools/e2e/S_array.{0,1,3,4}.out`, `S_array.2.first.out`, `S_array.2.resume.out`, `C_collect.partial.out`, `C_collect.final.out`. Memory probe logs: `pkg_tools/mem_3897.log`, `pkg_tools/mem_2134.log`. The in-process ctypes reading in those logs shows 0 MB because of a handle-type slip in the probe; the peak values quoted above come from Windows' process table: 85 MB for 3897 and 56 MB for 2134.
